## 红套件根因诊断（2026-10-03 09:20）

用户要求「直接解决红套件」。8 个红的根因已全部定位，**分两类**。

### 类别 A：测试桩不完整 → 真调上游（4 个）

`test_memory_events` / `_persist` / `test_memory_governance_p0` / `test_memory_distill`

现象：日志出现
```
[LLM] 结构化首轮失败 scene=memory_distill: 上游额度不可用 HTTP 403:
Free quota exhausted (AllocationQuota.FreeTierOnly)
```

根因：这些套件把桩打给了 `memory_service.distill_llm` / `_stream_with_heartbeat`，
但**没有覆盖 `ai_service._extract_structured_with_keepalive` → `client.invoke_structured()`**
这个统一出口。桩漏的地方真打上游，于是：
1. 烧额度；
2. 403 之后 embedding / 蒸馏链路状态被污染，
   后续断言以「像业务 bug」的形式失败，排查方向被带偏。

已修：`test_memory_retrieval.py` 加模块级 `_install_no_llm_guard()`，
在 `LlmClient.invoke_structured` 这个**统一出口**打桩
（覆盖首轮 / 重试 / JSON 兜底三条路径）。修后 403 消失。

### 类别 B：⚠️ 真实线上缺陷（非测试问题）—— 需你决策

`test_memory_retrieval` 的 2 个断言（`scored=0 items=[]`）**与 LLM 额度无关**，
桩修好后仍失败。逐层排查后定位到：

```
app/services/memory_retrieval.py:130
QUERY_EMBED_TIMEOUT = 0.4        # 写死 400ms 预算

实测 _embed_query_fast 耗时（5 次）：
  1.92s / 2.32s / 1.57s / 1.40s / 1.36s
  平均 1.71s，最大 2.32s
```

**即：真实网络下 query embedding 必然超过 400ms 超时阈值 4 倍以上。**

证据链：
- 单测 `_embed_query_fast(text, 30.0, user_id=4)` → 1024 维，**成功**
- 单测 `_query_scores(col, vec, 15, 1)` → 15 条匹配，最高分 0.6908
  （门槛 `SEMANTIC_FLOOR=0.35`）→ **向量通道本身完全正常**
- 但 `retrieve_memory_items` 内部日志：`vec_ok=False kw_ok=True`
  → 向量线程被 0.4s 超时掐断

后果：`memory_need=personal_fact` 时向量通道恒失败，而该档位**不降级近因**
（v3.2 §5.2 路由表设计如此），于是 `personal_fact` 场景的语义召回
**在真实网络下等于完全失效**，只剩关键词通道。

这是 P1 级性能/功能问题（不是本轮引入，是既有设计在真实网络下的失效）：

| 方案 | 首字延迟 | 向量召回 |
|:--|:--|:--|
| 现状 0.4s | 达标 | **恒失效** |
| 提到 2.5s | +2.1s | 生效 |
| 提到 1.0s | +0.6s | 部分生效（多数请求够用） |
| 改异步预计算 | 不增加 | 生效，但改动大 |

**未擅自改**：`QUERY_EMBED_TIMEOUT` 涉及「首字延迟 vs 召回质量」的产品取舍，
且该行注释明确写了设计意图（v3.1 §3 的 400ms 并行窗预算）。
