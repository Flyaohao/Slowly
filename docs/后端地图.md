## 2. 一个请求怎么走（这是最常用的部分）

以「发送一封信」为例，**请求只经过 5 层**：

```
① Android 客户端
   ↓ POST /api/v1/couple/letters
② main.py 中间件
   RequestLogMiddleware(130) → CORS(135) → DocsGuard(150) → SecurityHeaders(151)
   ↓
③ api/v1/couple/letters.py          ← HTTP 边界：解析、鉴权、错误码转换
   依赖: get_current_user(150 处用) + get_db(166 处用)
   ↓
④ services/letter_service.py          ← 业务逻辑：信怎么存、怎么校验
   ↓
⑤ repositories/letter_repo.py         ← 纯 SQL
   ↓
   MySQL
```

**各层职责（判断代码该放哪层）**：

| 层 | 只该做 | 不该做 | 数量 |
|:--|:--|:--|:--|
| `api/` | 解析请求、鉴权、**转错误码** | 业务逻辑 | 32 文件 |
| `services/` | 业务规则 | 直接写SQL、碰HTTP | 64 文件 |
| `repositories/` | **只有 SQL** | 业务判断 | 22 文件 |
| `models/` | 表结构 | 业务逻辑 | 27 文件 |
| `core/` | 基础设施 | 业务 | 8 文件 |

## 4. ⚠️ 禁区（改之前先确认）

| 文件 | 为什么危险 |
|:--|:--|
| `core/database.py` | `get_db` 被 **166 处**依赖。改它= 179 个路由全受影响 |
| `core/dependencies.py` | `get_current_user` 被 **150 处**依赖 |
| `models/` | 表结构改动需要 alembic 迁移，线上库不会自动变 |
| `memory_retrieval.py:154` | `chromadb.PersistentClient` 跑在**同一进程同一磁盘**。加 `--workers` 会让多进程写同一目录→ 数据损坏 |
| `llm_client.py` | 1171 行，但 `except` 都是窄异常且**有意的**。它做过兼容重构，乱动会破 |

**已修复（2026-10-02）**：

| 位置 | 改动 |
|:--|:--|
| `users.py:49` `upload_avatar` | `async def` → `def`；`await file.read()` → `file.file.read()` |
| `museum.py:28` `upload_image` | 同上。附注：`museum` 模块有 `require_feature` 依赖，默认冻结（返回 10006），与本改动无关 |

**保留 `async def` 的 3 处（都是正确的）**：

```
app/api/v1/couple/ai.py:169            _disconnect_watcher  ← 后台任务，需 async
app/api/v1/couple/mediation_room.py:183 _disconnect_watcher  ← 同上
app/api/v1/couple/ws.py:20             websocket_endpoint   ← WebSocket 必须 async
```

**读文件为什么改 `file.file.read()`**：`UploadFile.read()` 是 async 方法，同步路由里不能 await。
底层 `UploadFile.file` 是 `BinaryIO`（SpooledTemporaryFile），同步读是 FastAPI 官方用法。

## 5. 出问题怎么查

| 症状 | 先看 | 再看 |
|:--|:--|:--|
| 某个接口 500 | `main.py:294` 全局异常处理 → 日志里的 traceback | 该路由的 service |
| 客户端拿不到业务码 | `core/errors.py` `safe_business_code` | 路由里 `ApiResponse(code=...)` |
| AI 没返回 / 卡住 | `llm_client.py` 超时 120s | `ai_service.py` + worker 日志 |
| 数据没存上 | `ai_task_worker` 是否在跑 | `ai_task_repo`任务状态 |
| 登录失败 | `core/dependencies.py` + `core/crypto.py` | JWT 解码 |

## 7. 测试现状（2026-10-02 最终实测）

全量 85 个套件，**75 通过 / 10 失败**。

### ⚠️ 真调 LLM 的套件远不止 5 个

`tests/live_llm_guard.py` 原本只覆盖 5 个套件，实际有 **17+ 个套件会真调但没守卫**。
**无 key 时它们在下游短路返回，看起来像「通过」；一配 key 全部复活并烧额度。**

已补守卫（守卫总数 5 → **10**）：

| 套件 | 单次上游调用量 |
|:--|:--|
| `test_agent` | **6+ 次**（Agent 多轮工具调用，最容易烧） |
| `test_generation_stream` | 4 类流式端点各 1 次 |
| `test_ai_live` | 多场景循环 |
| `test_profile_ab` / `test_rag_inject` | 各 2 次对比 |

反向扫描确认无漏网：`test_ai_field_contract` 是 **AST 静态扫描**（只解析源码不执行）、
`test_fallback_config_500` 无模型调用、其余 7 个有自有桩。

### 10 个失败的真实原因（全部经对照实验或字节级验证）

| 套件 | 原因 | 性质 |
|:--|:--|:--|
| `test_get_db_async_dependency` | 3 项断言全在验已回退的 `get_db` 改 async | **建议删除** |
| `test_mediation_task_queue` | `sqlite3 no such table: mediation_room`（harness 没建表） | 既存缺陷 |
| `test_memory_retrieval` | 清空 key 后 rc=0 → **依赖真实 AI 配置** | 已定性 |

| `test_memory_events` / `_persist` / `test_memory_governance_p0` / `test_memory_index_cas` | AI 源桩未被调用 → `IndexError` / `scored=0` | 同源，**已确认非本轮改动**（`git stash` 对照实验验证） |
